# 002 授权

授权决定谁可以开始工作，以及这份工作可以包含什么。本文建立在 [001 领域模型](001-domain.md) 之上。

宿主执行允许名单、规则和授权。消息、评论、被引用的文档都只是决定的输入，它们不能改变这些权限。

## 触发的两条路径

### 评估：决定是否开始工作

来源会记录一条消息是否在找智能体：@ 机器人或智能体账号记作 `mention`，私聊记作 `direct`。准入环节检查发送者和该来源的策略：

- 名单上的人对智能体说话，构成一次明确请求。
- 人在已经有工单的线程上追问，按下面几节的规则处理。
- 其他人的消息按其接收范围使用准入表。
- 来源机器人名单上的机器人可以产生推断候选，永远不会构成明确请求。其他机器人不予准入。

### 订阅：延续已有工作

已订阅线程上的每条消息都作为上下文到达订阅它的工单，包括机器人消息和 CI 消息。这条投递绕过准入，也不授予任何新权限。每张工单仍受它的授权约束。

人在某张工单自己线程上发的消息，由那张工单的执行器决定怎么处理。主 Session 把消息挂到某张工单上时也一样。只要消息归执行器所有，它就不经过评估，也拿不到决定。每个执行器要么在工单范围内处理该请求，要么把它交回，去别处路由。

归属关系在工单存活期间持续，即使有人移除了它的订阅。归属也覆盖已被某人结束、但没有被人停止、且有消息在等它恢复的工单。

主 Session 会收到一条追问通知。消息归执行器所有期间，主 Session 只能在人的要求下停止工作；接单、挂接、忽略、重新入队都会被拒绝。停止仍需经过准入，强度按下面说的追问强度处理。

### 交回与释放追问

执行器在以下两种情况会交回消息一次：请求超出了工单范围，或者这条消息属于另一张工单。工单保留它的订阅。如果被挂接的线程无关，执行器会交回它在那里拥有的消息。

只有当没有任何工单还拥有这条消息时，它才会进入一次新的评估。它的候选里包含各执行器给出的理由。准入环节把它当作该线程上的一条普通消息来判断，主 Session 可以接单、挂到别处或忽略。交回一条工单本就不拥有的消息（例如机器人消息，或已经送进评估的消息）不会排队任何东西。

工单结束时，它会释放执行器没有读过或没有接手的追问。这包括从未投递给执行器的消息，以及在它最后一次报告或轮次结束之后投递、而它既没确认、没回答、也没交回的消息。只要没有别的工单拥有它，每条被释放的消息就进入评估。停止只结束被停止那张工单的工作。

被停止的工单不会把它的停止消息再次送给评估，除非另一张工单把它交回。执行停止的主 Session 可以把消息剩下的部分当作新工作接单。

人可以在面板上把一条有归属的追问送进评估。如果主 Session 之后又把它挂回一张存活的工单，执行器会再次收到它。当没有任何有效判断覆盖这条消息时，面板也会提供重新评估。

### 仅作上下文的订阅

执行器可以为了上下文跟随一个相关线程，例如另一个 Issue 或 pull request。它的消息会到达工单，但不授予权限，也不提供追问强度。除非主 Session 把某个消息从那个线程挂接过来，否则那里的人的消息不会恢复已结束的工单。主 Session 关于其他工作的提示也仅是上下文。

到达不了任何工单的人的消息，包括工单被人停止的线程，走评估路径。机器人消息也走评估路径，与它们投递给已订阅工单是相互独立的。

## 强度

| 强度 | 情形 |
| --- | --- |
| explicit 明确 | 名单上的人对智能体说话，或在已有工单的线程上追问；准入表中设为"明确请求"的单元格 |
| inferred 推断 | 不在名单上的人在带工单的线程上追问，除非其对应单元格是"明确"；准入表中设为"推断候选"的单元格；来源机器人名单上的机器人发出的、对智能体说话或到达来源"收全部消息"位置的消息 |
| not admitted 不准入 | 其他任何机器人的消息、准入表忽略的一切，以及接单模式为 `off` 时的所有推断情形 |

对不在名单上的人，明确的准入单元格优先级更高，即使在带工单的线程上也照样生效，并且在任何接单模式下都可用。否则其追问是推断强度，在 `off` 模式下不予准入。仅作上下文跟随的线程上的消息使用准入表，而不使用追问强度。

## 准入

每个来源的策略都有一张准入表。它的行是接收范围：

- **飞书：** 每个配置过的会话、机器人从中收到 @ 的其他会话，以及私聊。只有当飞书卡片上的 **其他群** 设为 **仅 @** 时，其他会话才会被接收。
- **GitHub：** 新 Issue、新 pull request、评论，以及默认分支的 CI。

一行最多三个单元格。每个单元格决定一条消息变成明确请求、推断候选，还是什么都不算：

| 单元格 | 可选值 | 默认 |
| --- | --- | --- |
| 在名单上，未对智能体说话 | inferred、ignore | inferred |
| 不在名单上，对智能体说话 | explicit、inferred、ignore | ignore |
| 不在名单上，未对智能体说话 | inferred、ignore | ignore |

未被点名的消息（"未对智能体说话"）的单元格，只在来源收全部消息的地方可用，例如设为 **全部消息** 的飞书会话，或开启了"接收全部"开关的 GitHub 范围。CI 结果没有发送者，所以它那一行只提供最后一个单元格。机器人消息改用机器人名单，而不是这些单元格。

把"不在名单上、对智能体说话"的单元格设为 explicit，就等于允许该范围内任何人 @ 智能体来请求工作。这对专门的答疑群有用。推断候选仍取决于接单模式。追问通常绕过这张表，但明确单元格依然授予明确强度。

准入表是策略版本的一部分。放宽某个单元格不会立即停掉据此接单、正在跑的那些工单。当它们恢复前重新校验时，可能因此被吊销授权。

### 机器人与自动化评审者

宿主把 GitHub App、以 `[bot]` 结尾的登录名、以及飞书机器人识别为机器人。来源可以列出诸如 `dependabot[bot]` 的机器人，让它们的消息可以成为推断候选。它们必须要么对智能体说话，要么在收全部消息的范围内发帖。它们不能发出明确请求，也不能停止工单。

使用普通账号的自动化评审者，对宿主来说仍然算作一个人。它的评论会到达已订阅的工单并产生追问通知。团队提示词必须把这类账号标明为自动化评审者。

## 路由候选

主 Session 用 `orchestrator_route` 路由明确候选。一次调用可以包含多个接单、挂接、停止或忽略决定。每一项独立处理：某一项被拒或缺字段，不影响其他项执行。

推断候选通常需要完整研判。只有一个捷径：如果它的卡片显然没有触及任何已启用规则（例如闲聊或无关讨论），主 Session 可以直接忽略。决定会记录 `ignoredFromCard`，以区别于按规则研判。主 Session 在它的策略提示词小节里读取已启用的规则。

接单推断候选永远需要研判。直接接单会拒绝准入环节未认可为明确的触发。

## 接单模式与规则

接单模式是策略的一部分：

| 模式 | 效果 |
| --- | --- |
| `off` | 任何推断出来的东西都不成为候选，例如未点名消息、机器人消息、不在名单上的人的追问 |
| `observe`（默认） | 推断候选会被研判；正面研判记录为标记"本应接单"的忽略，不接单任何东西 |
| `auto` | 推断候选得到正面研判时就会被接单 |

明确请求在任何模式下都可用。先从 `observe` 开始，看过记录下来的决定之后再切到 `auto`。每次研判对每条已启用规则只判一次，无论是否命中。主动接单至少要求命中一条规则。

每条规则描述一类主动发现的工作。工单的授权记录命中的规则，它的执行器会收到这些规则的名称和说明。

对那张工单，规则里的流程与沟通要求会覆盖默认值。一条"保持沉默"的规则可以压掉确认消息；一条"评审"规则可以指定必须的评审人和合并前的批准。适用于所有工单的要求应该写进团队提示词小节。

## 策略版本

规则、接单模式和每个来源的策略共同组成策略版本。每个授权都记录它接单时所处的版本。

版本变化会作废正在运行的评估，并把它们的触发重新入队。它还会向每个受影响的存活工单发送一条"策略变更"输入。这条输入会说明属于哪种情况：

- 命中的某条规则变了（含新文本），或已不再适用；
- 请求者可能已不能再发起工作；或
- 主动工作不再被接受，例如模式从 `auto` 改了。

未受影响的工单不会收到通知。这个变化不会立即吊销存活工单的授权。

来源配置与策略分开。它控制什么进入系统：读哪些会话、某个范围是收全部消息还是只收 @。授权记录它的来源和接收范围。恢复时要求来源仍在监听该线程，但不要求它仍然接收那里的全部消息。

来源关闭期间，回复会等待；如果来源已不再监听目的地，回复会被丢弃。

"执行器对自己的结果可以做什么"这类条件（例如什么时候可以合并）不决定谁可以授权工作。它属于智能体的指令，不属于策略。

## 恢复与停止

已结束的工单保留它的授权。人在它某个线程上发消息，就能恢复同一份工作，不需要新的评估或决定，无论发送者是谁。机器人和 CI 不会唤醒已结束的工单。执行器判断该请求是否符合范围，不符合就结束这一轮。

只有三种操作会改变授权：接单创建它，人的停止撤回它，重新校验失败吊销它。被人停止的工单保持结束状态，不再收到任何东西。在那里请求工作需要重新接单。

### 恢复前的重新校验

来源必须仍在监听原来的线程。其余检查取决于授权的依据：

- 明确追问得来的授权，通过。
- 推断得来的授权，需要 `auto` 模式，且命中的规则仍然启用。
- 由准入表单元格批准而得的授权，按今天的表和发送者的名单身份，必须仍能得到至少原来的强度。因此，把某个发送者从名单上删掉，可能会吊销通过"名单内发送者"单元格接下的授权。
- 机器人得来的授权，要求该机器人仍在来源的机器人名单上。由推断表单元格和机器人得来的授权，还需要 `auto` 模式和命中的规则仍启用。
- 其他授权，要求发送者仍在来源的允许名单上。

重新校验失败时，工单保持结束状态，并且不接受任何在等它的消息。每条消息都视作没有到达任何工单；如果没有别的工单拥有它，它就进入评估。主 Session 不会被告知它到达了某个执行器。处理暂停结束之后同样如此。挂接到该工单会被拒绝，继续工作需要重新接单。

- **人在线程里说"停"是一个普通触发**，由评估决定是否停止。执行器不能声明"有人叫它停"。
- **面板上的停止是一条命令。** 它直接作用于工单，并记录为人工停止。
- **需要等待的条件属于来源。** 诸如"N 小时内无人受理"这样的条件，应该是一个自己等待并再次检查的来源；评估永远不等待。

## 评估没有跑完时

时限从候选到达主 Session 开始算。等待投递的时间不计入，未投递的候选永不过期。

超时的评估会把它的触发重新入队再试一次。连续重试两次之后，第三次超时记录 `unavailable`。研判失败也记录 `unavailable`；之后的新触发可以开启新的评估。策略发生变化、或决定是基于过期策略做出的，也会记录 `unavailable`，并立刻用当前版本把这批触发重新入队。

`evals` 健康条目报告最近一小时内未解决的 `unavailable` 决定。`scripts/dsh-superagent status` 会带上这个错误。

只有当那条 `unavailable` 决定距今不到 24 小时、仍是该线程上最新的决定、没有被忽略、且线程既没在排队也没在评估时，面板才会要求人工处理。人可以重新评估该触发，或忽略这个问题。
