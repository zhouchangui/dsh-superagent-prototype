# 安装设置

这是给"与操作者一起安装 dsh-superagent"的智能体的说明。如果你是人，请让你的编码智能体读这个文件并照做。

## 怎样执行安装

安装遵循 [000 设计理念](000-philosophy.md)：尽量少占用操作者的注意力。

- **问第一个问题之前**，只读本文件和 [000 设计理念](000-philosophy.md)，并把下面的探测跑一次。所有答案收集齐之前，不读别的东西。
- **一条消息只问一个问题**，只问一件事。等到答案再问下一个。探测已经回答的问题就跳过。
- **每条消息控制在 300 字以内**，除非操作者要求更多。每个问题都给出一个推荐答案（操作者用一个词就能接受），再用一句话说明它为什么重要。
- **提问期间不执行。** 先收齐所有答案，然后用一条消息给出完整计划，操作者确认后再执行。
- **永远不要在聊天里索要密钥。** 需要操作者亲自动手的步骤（创建账号、给 CLI 登录、填写应用的 secret），写进一条消息里，给出在操作者自己的终端中要执行的确切命令。
- **通过问题来讲清理念**，一次一句，不要做演讲。

## 1. 探测

在这个代码库里跑一次，结果自己留着：

```sh
node -v; pnpm -v; git --version; tmux -V; python3 --version; gh --version | head -1; dsh --version
gh api user --jq .login
command -v lark-cli
grep -l -E 'id: dsh-superagent\b' "${DSH_HOME:-$HOME/.dsh}"/profiles/*/cordis.patch.yml 2>/dev/null
```

- **前置条件：** Node.js 22.19+ 或 24+、pnpm、git 2.32+、tmux、Python 3.8+、GitHub CLI 2.48+，以及版本落在 `package.json` 的 `engines.dsh` 范围内的 DSH。缺哪一项，就写进计划的一条，而不是变成一个提问。DSH 还需要一个模型提供方；如果操作者从没用模型跑过 DSH，配置模型属于操作者步骤。
- **操作者登录名：** `gh api user` 的结果就是操作者自己的 GitHub 登录名，用作第 5 个问题的推荐答案。
- **已有 profile：** 如果某个 profile 已经有 `dsh-superagent` 条目，说明之前装过：问是否接着它继续、是否保留它的配置，并阅读 [006 部署](006-deployment.md) 的升级一节。

## 2. 提问

按下面的顺序提问，一条消息一个，跟着 [001 领域模型](001-domain.md) 里工作流的方向走：先问触发从哪来，再问在那里谁可以要活干，最后问执行器拿到工单怎么做。推荐答案写在方括号里。

**来源：请求从哪来。**

1. **来源。** 智能体只从 GitHub 接请求，还是也从飞书会话接？［只接 GitHub，除非团队本来就在飞书里干活。］
2. **仓库。** 智能体该在哪个 github.com 仓库上干活，写成 `owner/name`？
3. **智能体账号。** 智能体以哪个 GitHub 用户账号行动？［专用账号，绝不用操作者本人的：智能体写下的所有内容都会挂在这个名字下。］这个账号可能还不存在；创建它属于操作者步骤。
4. 有飞书时：**哪些会话**，按名称？机器人配好之后，智能体自己去查它们的 id。

**策略：谁可以要活干。**

5. **在 GitHub 上。** 哪些 GitHub 登录名可以向智能体要活干？［只有 `<operator login>`：智能体只替名单上的人行动，名单短一些，既能压低团队里的噪音，也方便操作者观察智能体的行为。］
6. 有飞书时：**飞书里谁可以提？**［第一个会话里的所有人，与该会话的成员保持一致。］

**执行：智能体拿工单做什么。**

7. **检出目录。** 每张工单应该从仓库的哪个本地克隆检出？［`~/src/<name>` 下的新克隆。］
8. **提交身份。** 智能体的提交应该以谁为作者？［智能体账号，这样它的工作是它自己的。］其他身份（例如操作者的）写进 Delivery requirements 提示词小节。
9. **自动合并。** 智能体自己的 pull request 就绪并获批之后，要不要自己开启自动合并？［不要：先由人来合并，等智能体的 pull request 稳定一段时间之后再说。］智能体从不以智能体账号的身份开启自动合并，所以选"要"时它需要一个能合并的另一账号的 GitHub CLI：请操作者在操作者步骤里登录一个，并在 Delivery requirements 里写明。选"不要"时，把 Delivery requirements 里的自动合并段落删掉。

有明显默认值的东西不要问，写进计划里代替：

- profile 叫 `superagent`，是 DSH Web profile 的副本，与操作者日常使用的 profile 分开，这样重启时不会关掉他们的 Session；端口 `3082`；状态目录 `<home>/.dsh/state/superagent`，用绝对路径；
- 从操作者自己的 profile 里做每小时检查，dsh-superagent 没在跑时把它修起来；
- 分支前缀 `agent/`；
- 接单模式 `observe`，它只记录主动发现的工作而不去做，以及默认的规则与提示词小节；
- 有飞书时：机器人只读 @ 提及，私聊开启。

## 3. 计划

发一条消息，300 字以内：要装什么、账号与 CLI、要保存的设置、操作者步骤、以及默认值。请操作者确认一次。

## 4. 执行

1. **先做操作者步骤。** 读 [006 部署](006-deployment.md) 的账号一节，自己写好 CLI 包装脚本，然后用一条消息说明只有操作者能做的事：创建智能体账号；如果用自动合并，登录一个负责开启它的账号的 CLI；以智能体账号接受仓库邀请；为每个包装脚本执行 `auth login`；用飞书时创建并发布机器人应用，并带着 secret 执行 `config init` 命令。等操作者说做完了，再用 `<wrapper> api user --jq .login` 逐个核对登录。
2. **安装并启动。** 按 [006 部署](006-deployment.md) 的安装、机器配置、启动与停止几节操作。跳过本仓库的 `git clone`：你已经在这个代码库里。如果第 7 个问题要求新建克隆，就克隆第 2 个问题里的仓库。已有 profile 时，跳过 `dsh superagent --from-default-profile` 命令，它会替换 profile 并删掉它的 `cordis.patch.yml`；改为编辑那个文件，不要替换它。
3. **设置。** 通过 [006 部署](006-deployment.md) 的管理 API 保存，顺序是：`github` 来源；用飞书的话再存 `feishu` 来源；带允许名单的 `policy` 块（飞书的话，先用机器人的 CLI 查出会话 id）；带第 7 个问题答案里那个 prepare 命令的 `executor` 块。然后保存提示词，把第 8 个问题的提交身份和第 9 个问题的自动合并答案写进 Delivery requirements。返回 `restarting: true` 的保存会重启 dsh-superagent：等到 `scripts/dsh-superagent status` 不再以 1 退出，再发下一个请求，并从 `GET settings` 重新读一次版本号。
4. **失败。** 被拒绝的保存会在响应体里指出是哪个设置问题。到 [006 部署](006-deployment.md) 的故障排查表里找到它，修好后继续。只有自己修不了的，才去问操作者。

## 5. 验证与交付

`scripts/dsh-superagent status` 以 0 退出，且没有设置问题。如果你运行在操作者自己的 DSH profile 里，就用你的排程工具创建 [006 部署](006-deployment.md) 每小时检查一节里的检查；否则把它的提示词交给操作者，让他们在那里排程。然后发一条消息，300 字以内：

- 面板的 URL，以及侧边栏里的 **Superagent** 条目就是去看的地方。
- 怎么试：用允许名单上的账号，在仓库的某个 issue 下评论 `@<agent login> <request>`。大约一分钟内概览页就会出现一张工单。
- 给操作者的三条规则，出自 [000 设计理念](000-philosophy.md) 的责任一节：从窄处开始；为了更少的噪音不断调；对智能体说的话负责。
- 进一步阅读：[docs/](000-philosophy.md) 里的编号文档（英文原文），按顺序读。
