# 003 执行

本文跟着一张已接单的工单，走过执行、投递与恢复。它建立在 [001 领域模型](001-domain.md) 与 [002 授权](002-authorization.md) 之上。

## 工单阶段

每张未结束的工单有一个阶段，由它在等什么决定。从上往下读这张表，第一条命中的行生效。

| 阶段 | 条件 | 面板标签 |
| --- | --- | --- |
| person / delivery | 向执行器 Session 投递输入失败；2 秒后重试，之后延迟翻倍直到一分钟，一次成功、新的派工或工单结束都会清除它 | Input undelivered |
| person / answer | 它有"待人工决定" | Awaiting answer |
| person / review | 最新的报告是 `ready` | Awaiting review |
| person / blocked, failed | 最新的报告是 `blocked` 或 `failed`，且之后没有人的消息到达该工单 | Blocked · Failed |
| working / queued | 没有派工，或派工处于 pending | Queued |
| idle | 最新的报告是 `waiting`，或派工已结束 | Waiting for a Trigger |
| working | 其他所有情况 | Working |

`person` 阶段表示工单没有人的输入就无法继续。一条新的消息会释放 `blocked` 或 `failed` 的工单给它的执行器，于是它移到下一个命中的阶段，通常是 `working`。

`idle` 工单已结束它的一轮，没有悬而未决的问题。已订阅线程上的触发可以让它继续。

## 执行器

每张工单得到一个名为 `worker-<ticket id>` 的执行器 Session，以及一个以工单短名命名的目录。目录建在配置的执行根目录下，默认是 `<stateDir>/work`。

执行器 Session 以操作者的操作系统用户身份、无需批准地运行命令。它的 `dsh-superagent-worker` 预置里含工作所需的工具，并在 5 秒后把前台 shell 命令转到后台任务。这样工作节点能在下一步就收到新消息，而不必等一条长命令跑完。

主 Session 使用 `dsh-superagent-router`，同样的 5 秒 shell 与 job 等待上限，工具集更小，专为路由而设。Session 会保留创建时所选的预置。工作节点的子智能体使用 DeepSeek-Harness 的 `standard` 预置。

### 后台工作与工作节点槽位

当一轮结束时仍有 shell 任务或子智能体在跑，工单继续占着工作节点槽位，并保持"执行中"。它不会被报告为等待，主 Session 也收不到等待报告。任务或子智能体完成后，会在同一个槽位里带着结果唤醒执行器。一轮结束时已无后台工作，执行器才会正常报告等待。

每一轮之后，后台工作最多有 30 分钟完成。到达上限时，shell 任务被杀死，工单报告为等待。报告包含执行器最后说的话，以及哪些任务被杀、哪些子智能体仍在运行。子智能体允许继续。执行器在下一轮读被杀任务的结果。

向人交接会立刻释放槽位，并让报告继续生效。这适用于 `ready` 报告或提问之后（除非此后又有输入到达），也适用于任何 `blocked` 或 `failed` 报告之后。

交接时，子智能体停止。shell 任务（例如留待评审的服务器）可以继续运行，直到派工结束。它们不占槽位，也不受 30 分钟上限约束，包括在后续轮次之后。它们的完成不会唤醒执行器；执行器在下一轮去读结果。

人也可以直接在执行器 Session 里写话，从而开启一轮。它的后台工作遵守同样的规则。

派工结束时，它的 shell 任务会被杀死，且不唤醒 Session。它的子智能体被释放，它们唤醒的任何完成轮次都会被丢弃。替代它的派工和等待中的输入在关闭流程结束后才开始。

在 DeepSeek-Harness 进程内停止或重启插件，走的是同一条关闭路径。尚未进入 Session 历史的输入会保留。关闭时为每个工作节点的后台工作最多等 10 秒；进程重启则直接结束这些工作。繁忙中被中断的派工会带着恢复说明重新开始。

工作节点的子智能体（包括嵌套的）使用 DeepSeek-Harness 的 `standard` 预置，权限与工作节点相同。它们只保留工作节点被允许的工作工具，工单结束时失去这些工具。在 `standard` 下，shell 命令 60 秒后转到后台。子智能体结束时它自己的任务会被杀死。

### 准备工单目录

首次派工之前，如果工单目录不存在，prepare 命令会在执行根目录下用 `sh` 运行一次，十分钟内必须完成。没有 prepare 命令时，工作节点在一个空目录里开始。

命令失败会让工单失败，并记录它的输出。重试或人在工单某个线程上发消息，会再次尝试准备。典型命令用 `git worktree` 建一个检出。当 pull request 分支的最后一段路径与工单短名相同时，这个 pull request 就归该工单。

### 并发

工单从启动那一刻（含准备工作）开始占一个工作节点槽位，或者从唤醒它空闲执行器的那次投递开始占用。它在整个活跃轮次中也占着该槽位。

配置的并发上限针对这些槽位，另有一个额外槽位留给人的消息或状态查询。正常槽位占满时，这类唤醒可以使用额外槽位；在新启动之前，它会优先占用下一个空出来的槽位。因此新工作不会阻止人继续推进已有工单。

其他输入（例如 CI 结果）排队等正常槽位。启动在 `working / queued` 里等槽位空出来。启动是并发执行的，所以一个慢的 prepare 命令只拖慢它自己的工单。

### 执行变量

prepare 命令与执行器指令收到相同的执行变量。命令读环境变量；执行器在提示词里读这些变量的值和说明。都不含凭据。

| 变量 | 注册者 | 值 |
| --- | --- | --- |
| `DSH_SUPERAGENT_DIR`、`DSH_SUPERAGENT_NAME`、`DSH_SUPERAGENT_TICKET` | 执行器 | 工单的目录、短名与 id |
| `DSH_SUPERAGENT_BLOCKED_COMMANDS` | 执行器 | 执行器不得运行的命令 |
| `DSH_SUPERAGENT_GITHUB_REPOSITORY` | GitHub | 来源监听的仓库，`owner/name` |
| `DSH_SUPERAGENT_GITHUB_ACCOUNT`、`DSH_SUPERAGENT_GITHUB_COMMIT_EMAIL` | GitHub | 智能体账号及其提交邮箱 |
| `DSH_SUPERAGENT_GITHUB_NUMBER`、`DSH_SUPERAGENT_GITHUB_PR_HEAD` | GitHub | 启动该工单的 Issue 或 pull request，以及后者的 head ref |
| `DSH_SUPERAGENT_FEISHU_BOT`、`DSH_SUPERAGENT_FEISHU_CHAT` | 飞书 | 机器人，以及启动该工单的会话 |

工单相关的值来自它的目录和发起它的触发。其他值来自当前的部署设置。只有面板能修改执行环境设置；发给主 Session 的文本无法改变已配置的 shell 命令。

工作节点通过智能体账号的 `gh` 访问 GitHub，通过机器人的 `lark-cli` 访问飞书。被禁的命令按名称调用时会失败。

这些包装脚本和目录只是建立默认值，不是安全边界。工作节点仍然可以用绝对路径执行程序。

## 合并

自动合并由 **Delivery requirements** 提示词管辖。宿主没有针对合并的专门决策逻辑。

默认情况下，执行器绝不以智能体账号的身份开启自动合并：GitHub 会把合并记在开启它的人名下。Delivery requirements 必须指定另一个账号的 CLI 用于合并。没有这个 CLI，就由人来合并 pull request。

默认指令只在以下情况允许自动合并：该 pull request 是为这张工单开的；它已就绪；所需批准覆盖 head commit；且新增加删除不超过 200 行。推新的修订之前，执行器会撤销自动合并。

没有正文的评审（例如批准）同样作为触发到达，可以唤醒正在等评审的执行器。这些指令约束智能体，不约束 GitHub 的合并规则。要强制批准，就在分支保护里要求批准并作废过期批准。去掉合并 CLI 或删掉自动合并段落，就转回人工合并。

## 工单怎样结束

- **就绪但没有 pull request：** `ready` 报告把工单以"已完成"结束。
- **无事可做：** 执行器发现没有需要人处理的工作（例如请求无法复现、或已被取代）时报告 `dropped`。工单不发消息就结束，除非命中的规则要求发一条；之后人在它线程上的消息可以恢复它。

### Pull request

一旦执行器报告了启动该工单的 pull request，工单就跟随它。从它分支开出的每个 pull request，在执行器报告、或 GitHub 来源发现之后，也会被跟随。重新打开的 pull request 会被重新跟随。

当它打开的 pull request 都不再处于打开状态时，工单就算完成。如果它没打开任何 pull request，则它跟随的所有 pull request 都必须已关闭。随后它按最近一次相关关闭的结果结束，并保留订阅，以便之后人的评论可以恢复它。

如果恢复、重试或恢复中的工作还没做完，关闭并不会结束工单。如果执行器确认或回答了一条它拥有的追问、但此后还没有发出非进展报告、也没有在读到该消息之后结束一轮，关闭同样会等待。之后一次 `ready` 报告在满足同样的 pull request 完成规则后结束工单。

会话类渠道会收到一条关于 pull request 结果的最终通知。GitHub 本身已经在 pull request 上显示了结果。移除工单对某个 pull request 的订阅，也就停止跟随它。

因此"待评审"（Awaiting review）意味着一次带 pull request 的 `ready` 报告。

### 追问与上下文线程

执行器决定工单自己线程上的人发来的追问。范围内的请求它自己处理，超出范围或属于别的工单的请求则交回。一旦没有执行器拥有该消息，它就变为主 Session 的候选。除此之外，主 Session 只能应人的要求去停止工作。

输入在 Session 把它带入某个步骤、并且随后报告或结束一轮之后，才算"已读"。工单结束时，未被确认、回答或交回的未读消息会回到评估，详见 [002 授权](002-authorization.md)。已经读过但因无需动作而留下的消息（例如道谢）则不会。

仅作上下文跟随的线程仍会投递消息，但不让工单拥有人类追问的处理权，也不会恢复已结束的工单。那些消息会被独立评估。

只要还有存活的工单在订阅，来源就会轮询已订阅的线程；在最后一次触发与订阅工单结束两者中较晚者的两周之后停止。此后消息只能经由普通入口到达：GitHub 通知或飞书实时事件。

## 失败与恢复

### 执行器受阻或失败

当执行器 Session 报告 `blocked` 或 `failed`，或启动失败、出错（记为 `failed`）时，工单不接受任何自动输入。

模型提供方或网络的短暂失败、HTTP 408、429、5xx，或连接被拒、被重置、超时，会先重试三次，退避时间递增：启动会重跑；轮次失败的工作节点会被要求继续；失败的 prepare 命令不会重跑。

一旦进入失败状态，CI 消息和机器人消息仍会记录在工单上，但不投递，也不唤醒 Session。

它的工具仍然可用，所以人可以直接在 Session 里继续工作。

启动失败不会自行重试。

人的消息、之后再来的既非 `blocked` 也非 `failed` 的报告、或者一次重试，都会解除这个挂起。

这一状态由存储的报告与输入推算得出，因此重启后依然保留。

### 重试

当未结束的工单处于 `person / delivery`、`person / blocked` 或 `person / failed` 时可用：新建一次派工，重新启动它的工作节点并接手等待中的输入，这三种情况的对策都是它。

一旦人的消息到达了受阻或失败的工单，执行器就拥有了该消息，工单显示为执行中（若失败启动重新开始时显示为排队），并且不再提供重试，除非投递那条消息失败。

重试会结束当前派工，并在同一个执行器 Session、目录、分支和 pull request 上开始新的派工。

执行器模型只在创建 Session 时生效；已有 Session 保留它的模型。

### 重启

正在运行的派工以"host restarted"结束，新的派工带着恢复说明开始，说明要求执行器在做任何对外动作之前，先检查它的目录、git 历史和 GitHub，从最早的工单开始。

处于等待、就绪、受阻或失败状态的派工保持不变，除非在那份报告之后又有输入到达；有的话它们也会重新开始。

Session、目录、订阅、待发消息和下面提到的存储工作都能挺过重启；每个执行器 Session 把哪些消息带入历史的记录也一样。一个步骤在认领消息之后、调用模型之前记录它：被重启打断的一轮所取走的消息，只要之后有报告或轮次结束，就算已读；而一个步骤认领了、却在进入历史之前被取消或出错打断的消息，算作未读。

重试或重启会把"投递给被替代的那次派工、但执行器 Session 没有取走"的消息（可能因取消或被截断的步骤而丢掉）重新交给新派工；仍留在 Session 里的副本（由重启保留，或跨崩溃持久化）会在新派工的第一条消息之前被取出，所以新的投递是唯一副本。

### 存储工作

dsh-superagent 在做出决定之后要做的事，例如把候选、追问或报告转给主 Session、启动派工、投递输入，都是先存储、后执行。

转达或投递失败（例如 Session 联系不上）会在 2 秒后重试，之后延迟翻倍直到一分钟；启动失败会让工单失败，除非那是上面说的短暂失败。

每一类工作只有在连续失败三次之后，才会作为概览页的系统问题报错；输入投递失败则显示在它自己的工单上。

发往主 Session 的转达保持顺序，通知也一样；一条失败会挡住同类的后续若干条。

### 来源失败

GitHub 来源逐个独立读取每个 Issue、pull request 和线程：一次读取失败会把错误留在它的线程上，下次轮询再读，并计入来源的错误数；默认连续三次轮询失败后才报告；任何一次成功轮询会重置计数。

智能体失去私有仓库权限时 GitHub 也回 404，所以 404 会重试。

被通知到的 Issue 或 pull request，如果读取一直失败，会在首次失败读取的一天后丢弃；GitHub 报告它已删除时则立即丢弃。此后它不再导致轮询失败，它的线程保留错误，来源状态里会点名它。

它的读取位置停在原处，所以之后的通知、或对它线程的轮询，会读到那些失败读取漏掉的内容。

飞书事件消费者会报告每一次失败；对已订阅话题的轮询则把每次失败留在对应的线程上。

GitHub 列表或飞书页面里格式错误的条目会被跳过，来源状态会计数。

### 渠道失败

外发消息作为存储工作保存并发送，从 5 秒开始退避重试，翻倍直到 300 秒。

一张工单发往同一个会话的消息按入队顺序发出，所以它的确认排在后面的答复或结果之前：当同一张工单发往同一会话的更早一条消息还没发出去时，这条就等着，直到那条连续失败三次并显示为问题。

其他工单的消息、以及不属于任何工单的消息，不会等它。

有失败尝试的消息会一直作为系统问题，直到发出或被撤回。

消息只在两种情况下被丢弃：来源已不再监听该会话，或来源回答该会话永远收不到它。来源关闭期间，消息会等待。

来源会在这些情况如此回答：GitHub 上 Issue 已删除或会话已锁定；飞书上的消息已撤回、或飞书已找不到该消息。

对已不存在的评审评论的回复，会改为发到该 pull request 的会话里。

被丢弃的消息保留记录，含丢弃时间、原因和它原本对应的工单，因此不会被重新入队；被丢弃的确认读作"已丢弃"，而不是"已发送"。

### 暂停处理

停止派发、新的评估、评估超时、输入投递和回复；已经在进行的启动会等到处理恢复。来源继续记录触发，正在跑的执行器轮次不会被打断。

人发给已结束工单的消息会等待：暂停后的第一轮会恢复该工单，前提是它的授权在当时策略下仍成立。

进行中的评估在暂停期间不会过期；它的截止时间按暂停时长相应后移。

### 配置无效

某个来源配置若被它的种类拒绝，该来源实例会被停用。
